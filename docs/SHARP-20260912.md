# SHARP reliability release — 12 September 2026

Baseline: `f1c0c13de7c97338fd90a22b8bf3d611a576ec1f`.
Candidate: `gpt-sharp/releases/20260912/index.html`.

## Product scope

The single accepted addition is Focused Daily. It selects six weak or neglected domains, repeats short blocks toward ten active minutes and finishes at a block boundary (typically about 10–15 minutes). Quick retains a weighted selection of six short blocks; Full Daily covers all 18 domains and the weakness bonus, with its existing recall/encoding flow. Practice does not change saved progression. No additional brainstorming features were included.

## Runtime

Scripts load explicitly in this order: dictionary → data → games → quality → controller → reflex → UI → app. No function is patched by a later layer and no recovery script is injected dynamically. Each phase invalidates its timers and animation callbacks. Events can settle a question once; callbacks also verify their originating session and generation. A block result is committed once under a stable session/block identifier.

Reflex keeps one mounted pad throughout a hold. Cancellation or lost capture is an interruption, not a correct reaction or false start. Pointer and keyboard input are supported and recorded; the input method cannot change during a block. Five valid trials finish immediately. Reflex retains a fixed protocol rather than awarding cosmetic levels.

Backgrounding, orientation changes and manual pause stop the clocks. The unfinished block restarts on continuation; completed blocks stay saved. Times use a monotonic clock and are armed at an animation-frame presentation boundary. This is a browser timing estimate, not a hardware measurement of the first illuminated pixel. Native iPhone keyboard/callout behavior still needs a physical-device check; mobile WebKit automation cannot reproduce every iOS integration detail.

## Content and scoring

Percentage calculations accept their exact decimal results. Numeric forms support decimals and an explicit sign toggle while retaining native keyboards. Matrix grids are screened for alternative supported row rules. Planning varies start/goal locations and requires a real detour, with independent shortest-path tests. Strategy excludes ties and chooses the actual best displayed expected value. Spatial patterns have eight distinct dihedral transforms; rule switching includes repeats, and analogy instructions do not disclose the answer relation.

Stroop runs balanced eight-trial blocks (two congruent/six incongruent), records omissions and reports unavailable interference when there are too few correct samples. Speed credit is gated by accuracy and uses correct-response latency. Promotions use evidence from the current level and scoring version. Sharpness stays within 0–100.

Scoring version 2 starts a new personal series. Existing values are preserved in each domain's `legacy` record when the new series begins; old history is retained and labelled previous series. Old minutes remain recorded separately because they measured elapsed time; new active minutes exclude result screens and background time. Historical results are not silently rescored.

The bundled challenge dictionary contains 5,127 spelling-list checked entries and 769 six-letter racks, each supporting at least 12 accepted words. Its licenses and source pins are included beside the asset. Membership is a finite challenge list, not a claim to accept every English word. There is no runtime external dictionary request or legacy fallback.

## Progress contract

The production keys remain `sharp-final-continuous-v1`, `sharp-final-quality-v1` and the legacy dictionary cache key `sharp-word-dict-v2`. Core schema version 2 embeds quality state, so the canonical save is one atomic localStorage write. The quality key is mirrored for older readers. Every write obtains a Web Lock and checks the previously read core and quality values before overwriting. A stale tab stops saving and offers export/load-latest controls. Browsers without Web Locks can train in memory and export; they display a save warning instead of performing an unsafe competing write.

State is validated, bounded and repaired defensively. A migration/repair/import recovery snapshot is saved under `sharp-final-backup-v2` before replacing existing data. If that backup cannot be written, original data is protected from overwrite. Future schema versions are not written over. Explicit export/import transfers core and quality together; import previews the replacement and backs up current progress first.

Checkpoints store completed blocks plus session identity, planned domains and active time. Resume repeats the unfinished block. Starting another session archives completed blocks as a partial session. Recent detail is bounded at 600 trial records and 60 session summaries; exports include those records with question snapshots, responses, errors, timing and build/scoring/dictionary versions. They cannot reconstruct trials that the old app never recorded.

Pending recall encoding is resumable and becomes due only after confirmation. Active word cues are unique. Failed recalls remain scheduled and do not retire the item.

## Validation and release

Run `npm ci --ignore-scripts`, `npm run test:static`, `npm test`, `npx playwright install --with-deps chromium webkit`, then `npm run test:browser`.

The static gate checks syntax, exact script order, unique function definitions, storage keys and content-hashed asset references. The Node suite uses fake time and a minimal DOM; its full-session checks do not establish browser layout correctness. Semantic tests independently recompute displayed arithmetic and Strategy answers, alternative matrix rules and shortest paths. The browser suite exercises actual DOM navigation, forms, Reflex hold/release, offline dictionary use, and a complete Full Daily timeout path in Chromium and WebKit.

`SHARP validation` runs on pull requests and pushes. Before switching the production entry point, inspect the exact candidate commit's regression result, then verify the deployed candidate in the browser. GitHub Pages' existing branch-based deployment is separate from the validation workflow. Repository-level enforcement of a required check and switching Pages to a validation-dependent Actions deployment require repository administration settings; the available connector does not expose those writes. Do not describe the existing Pages job as a test gate. All release changes in this handover are manually gated on a passing exact-commit validation result.

Run `npm run build:release` after candidate asset edits. This writes content-hash cache versions and `release.json`. Once the directory is selected by production, treat it as immutable and create a new release directory for subsequent changes. Do not add dependencies to the browser app's runtime.

For rollback, restore the production entry point to a previously tested release with a forward commit and verify Pages. Keep progress keys untouched. Reverting to the pre-version-2 app loses awareness of score-series labels and embedded canonical quality state; export current progress first and use the recovery snapshot for deliberate data restoration rather than silently resetting storage.
